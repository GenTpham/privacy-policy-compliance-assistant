## 1. System Classification

**System Type:** RAG

**Description:**
A RAG-based compliance chatbot that lets users — primarily compliance analysts, DPOs, and internal business teams — ask natural-language questions (in Vietnamese and English) about privacy policies and receive grounded answers with inline citations. The system indexes 17K+ passages from privacy policy documents into Qdrant using Nemotron embeddings, retrieves the top-k most relevant chunks per query, and synthesises an answer via Gemma 4 26B that cites only the retrieved passages by numeric ID. "Good" means: every claim in the answer is traceable to a verbatim excerpt from the corpus, the correct regulatory instrument is identified, and the system explicitly declines when the corpus does not support a confident answer.

**Critical Failure Modes:**
1. **Silent index gaps** — Ingestion fails partway (rate-limit, network error) without a reliable checkpoint; the resulting index appears complete but is missing batches. All downstream queries over those missing passages return "no policy found" silently — the system gives wrong answers invisibly.
2. **Wrong distance metric on collection creation** — The `policies` collection is created with DOT_PRODUCT or EUCLIDEAN instead of COSINE. Retrieval appears to work but ranking is wrong, returning plausible-but-incorrect passages. This failure is immutable — fixing it requires dropping the collection and re-ingesting all 17K passages.
3. **Citation fabrication** — The LLM generates answer text citing policy positions not supported by any retrieved passage, or invents chunk IDs not present in the retrieved set. In a compliance context, a user may act on a fabricated legal interpretation as authoritative.
4. **Metadata loss during chunking** — The `source_doc` or `title` payload field is dropped or corrupted during passage splitting. The system cannot attribute answers to source documents; citations degrade to "Unknown document" — unusable for compliance record-keeping.
5. **Embedding dimension hardcoding** — A hardcoded dimension value (768, 1024) that doesn't match Nemotron's actual output causes silent vector size mismatches or accepts wrongly-sized embeddings from a different model.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Legal / Regulatory Compliance (Privacy Law)

**User Population:** Compliance analysts, data protection officers (DPOs), and internal business teams at organizations operating under Vietnamese, regional, or cross-border privacy law. Users query in Vietnamese natural language against a corpus of privacy policy documents, typically to answer internal compliance questions or identify policy gaps before an audit or incident response.

**Stakes Level:** High

**Output Consequence:** Users act on answers as authoritative guidance. A wrong or unsupported answer about data retention, cross-border transfer requirements, or consent scope may lead to an organization applying an incorrect policy interpretation — exposing them to regulatory fines (Decree 13/2023/ND-CP penalties), failed audits, or data subject rights violations. In conflict-detection queries, a missed contradiction between two live policies can allow a non-compliant practice to continue unchallenged.

```
      applied as if binding under Vietnamese law) or omits the applicable jurisdiction entirely.
```

```
Good: For comparison queries, the answer surfaces contradictions from both documents, names each
```

```
Good: When retrieved passages do not contain sufficient grounding for a confident answer,

Bad:  System synthesizes a plausible-sounding policy position that is not supported by any

Stakes: Critical
Source: FEATURES.md — "compliance professionals trust a system MORE when it declines rather

```

```

Good: The vector index contains all ~17K passages from the authoritative corpus with correct

Bad:  Ingestion silently dropped batches due to rate-limit errors, duplicate-skipping bugs,

Stakes: High
Source: Phase 1 specific — INGEST-06 sanity check requirement in REQUIREMENTS.md; D-02 and
        D-03 ingestion decisions in CONTEXT.md.
```

### Known Failure Modes in This Domain

1. **Silent index gaps causing false negatives.** Ingestion scripts that partially fail (rate-limit timeouts, network errors) without a reliable checkpoint produce an index that looks complete but is missing batches. Compliance queries on missing passages return "no policy found" — not an error, an invisible wrong answer. Mitigation: checkpoint-per-batch with re-run verification (D-03 in CONTEXT.md).

2. **Distance metric misconfiguration producing plausible but wrong rankings.** If the Qdrant collection is created with DOT_PRODUCT instead of COSINE (or vice versa) and Nemotron vectors are not unit-normalized, similarity scores are computed on the wrong scale. Retrieval appears to work but returns subtly wrong top-k passages. A compliance analyst gets an answer grounded in the wrong clause. Mitigation: INGEST-06 sanity check — embed a known passage and assert it ranks #1 before any production queries.

3. **Cross-document retrieval collapse.** For conflict-detection queries, top-k results cluster around one document because it has higher lexical overlap with the query. The LLM then cannot detect a conflict that exists in a second document. This failure mode is invisible to the user — the system returns a confident "consistent" finding when a contradiction exists. Mitigation: explicit multi-document retrieval strategy and eval coverage of known cross-doc conflicts.

4. **Metadata loss during chunking.** If the ingestion script loses the `title` or `source_doc` metadata fields when splitting long passages into chunks, the LLM cannot attribute answers to their source document. Citations become "Unknown document" — which is non-compliant with the tool's core value proposition. Mitigation: metadata propagation test as part of ingestion verification (INGEST-03).

### Regulatory / Compliance Context

**Vietnam — Decree 13/2023/ND-CP (Personal Data Protection Decree)**
Effective July 1, 2023. Applies to any organization processing personal data of Vietnamese citizens, regardless of where the organization is located. Key requirements relevant to this system's corpus:
- Consent must be explicit, specific, and documented — the system must surface the exact consent clauses from policies accurately.
- Cross-border transfer of personal data requires a Data Transfer Impact Assessment (DTIA) — queries about data transfer rules are high-stakes.
- Data subjects have 11 enumerated rights (access, deletion, restriction, portability, objection, etc.) — policy Q&A on these rights must cite the correct applicable clause, not infer from GDPR equivalents.
- Automated processing of personal data (Article 2.13) that occurs on systems outside Vietnam is classified as a cross-border transfer — relevant if the AI system itself processes personal data from the corpus.

**Vietnam — Personal Data Protection Law (July 2025)**
Vietnam enacted a standalone Personal Data Protection Law effective July 2025 (superseding and building on Decree 13). Organizations operating under this corpus should be aware the legal landscape has evolved. The corpus indexed in Phase 1 should carry an "indexed as of" date in metadata to prevent stale-policy answers.

**GDPR (EU General Data Protection Regulation)**
Relevant if the privacy policy corpus includes policies from EU-operating entities. GDPR establishes rights and retention rules that differ from Vietnamese law — the system must not conflate them. Practitioners will flag any answer that applies GDPR rules to a Vietnamese-law context without explicit scoping.

**No direct AI-system regulation applies to this deployment** — the system is an internal compliance research tool, not a regulated AI product under the EU AI Act's high-risk categories (which covers AI in employment, education, critical infrastructure). However, if answers are used to make automated decisions about data subjects, Article 22 GDPR considerations may arise.

## 2. Framework Decision

**Selected Framework:** Raw Python — openai SDK 2.32.0 + qdrant-client 1.17.1 (no orchestration framework)

**Version:** openai==2.32.0, qdrant-client==1.17.1

**Rationale:**
The ingestion pipeline is a linear 3-step process: parse → embed → upsert. No orchestration framework is needed for this level of complexity. The `openai` SDK covers Nemotron embeddings via OpenRouter's OpenAI-compatible API (`base_url` override). `qdrant-client` provides the official async Python client for Qdrant. LangChain/LlamaIndex would add 30–40% overhead with no benefit for a single-collection, single-model pipeline. This aligns with the project constraint in CLAUDE.md explicitly prohibiting LangChain and LlamaIndex.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LlamaIndex | Explicitly prohibited by project constraint in CLAUDE.md; adds overhead for a linear pipeline |
| LangChain | Explicitly prohibited by project constraint in CLAUDE.md; 30–40% more boilerplate for no benefit |

**Vendor Lock-In Accepted:** Partial — OpenRouter API (mitigated: OpenAI-compatible, can swap base_url to OpenAI directly); Qdrant vector store (mitigated: Docker-hosted, not a cloud vendor)

### Entry Point Pattern

The following is the minimal working skeleton for Phase 1 ingestion: parse JSON corpus, probe embedding dimension, create Qdrant collection, batch-embed with rate-limit backoff, and upsert with a checkpoint file for resumability.

```python
"""
backend/ingestion/ingest.py
One-shot ingestion: load policy_qa_train.json -> embed via Nemotron -> upsert into Qdrant.
Run from project root: python -m backend.ingestion.ingest
"""
import asyncio
import hashlib
import json
import time
from pathlib import Path
from typing import Any

from openai import AsyncOpenAI
from qdrant_client import AsyncQdrantClient
from qdrant_client.models import Distance, PointStruct, UpdateStatus, VectorParams

from backend.app.core.config import get_settings

# ── Constants ──────────────────────────────────────────────────────────────────
COLLECTION_NAME = "policies"
BATCH_SIZE = 50           # conservative for OpenRouter free-tier (20 req/min)
MAX_TOKENS_WARN = 400     # warn if a passage exceeds this before embedding
CHECKPOINT_PATH = Path("ingestion_checkpoint.json")
DATASET_PATH = Path("dataset/json/train/policy_qa_train.json")

# ── Clients (initialised once per process) ────────────────────────────────────
settings = get_settings()

openrouter = AsyncOpenAI(
    base_url="https://openrouter.ai/api/v1",
    api_key=settings.openrouter_api_key,
    default_headers={
        "HTTP-Referer": "https://privacy-policy-assistant",
        "X-OpenRouter-Title": "Privacy Policy Assistant",
    },
)

qdrant = AsyncQdrantClient(
    host=settings.qdrant_host,   # "localhost" local dev; "qdrant" inside Docker Compose
    port=settings.qdrant_port,
    api_key=settings.qdrant_api_key,
)

# ── Tokenizer for C6 guard ────────────────────────────────────────────────────
_enc = tiktoken.get_encoding("cl100k_base")   # closest public tokenizer to Nemotron BPE

def token_count(text: str) -> int:
    return len(_enc.encode(text))


# ── Embedding dimension probe ─────────────────────────────────────────────────
async def probe_embedding_dim() -> int:
    """
    Nemotron's output dimension is NOT documented by OpenRouter or NVIDIA.
    Call the API once with a test string and read len(resp.data[0].embedding).
    This value must be used to configure the Qdrant collection before any upsert.
    """
    resp = await openrouter.embeddings.create(
        model="nvidia/llama-nemotron-embed-vl-1b-v2",
        input="probe",
    )
    dim = len(resp.data[0].embedding)
    print(f"[probe] Nemotron embedding dimension: {dim}")
    return dim


# ── Collection bootstrap ───────────────────────────────────────────────────────
async def ensure_collection(dim: int) -> None:
    """
    Create the 'policies' collection if it does not already exist.
    Distance.COSINE is correct for Nemotron (outputs L2-normalised vectors).
    CRITICAL: distance metric is IMMUTABLE after creation — wrong metric requires
    deleting the collection and re-ingesting all 17K passages.
    """
    existing = {c.name for c in (await qdrant.get_collections()).collections}
    if COLLECTION_NAME in existing:
        print(f"[bootstrap] Collection '{COLLECTION_NAME}' already exists — skipping.")
        return
    await qdrant.create_collection(
        collection_name=COLLECTION_NAME,
        vectors_config=VectorParams(size=dim, distance=Distance.COSINE),
    )
    print(f"[bootstrap] Created collection '{COLLECTION_NAME}' (dim={dim}, COSINE).")


# ── Checkpoint helpers ─────────────────────────────────────────────────────────
def load_checkpoint() -> set[str]:
    if CHECKPOINT_PATH.exists():
        data = json.loads(CHECKPOINT_PATH.read_text())
        return set(data.get("completed_hashes", []))
    return set()

def save_checkpoint(completed: set[str]) -> None:
    CHECKPOINT_PATH.write_text(json.dumps({"completed_hashes": list(completed)}))


# ── Embedding with exponential backoff ────────────────────────────────────────
async def embed_batch(texts: list[str], retries: int = 5) -> list[list[float]]:
    """
    Batch embed via OpenRouter. The 'input' parameter accepts an array — one
    API request covers the entire batch of BATCH_SIZE passages.
    Exponential backoff: waits 1, 2, 4, 8, 16 seconds on successive 429 errors.
    """
    for attempt in range(retries):
        try:
            resp = await openrouter.embeddings.create(
                model="nvidia/llama-nemotron-embed-vl-1b-v2",
                input=texts,
            )
            # resp.data items are ordered by index field — sort to match input order
            return [item.embedding for item in sorted(resp.data, key=lambda x: x.index)]
        except Exception as exc:
            if "429" in str(exc) or "rate" in str(exc).lower():
                wait = 2 ** attempt
                print(f"[rate_limit] 429 on attempt {attempt + 1}; sleeping {wait}s")
                await asyncio.sleep(wait)
            else:
                raise
    raise RuntimeError(f"embed_batch failed after {retries} retries")


# ── Main ingestion loop ────────────────────────────────────────────────────────
async def ingest() -> None:
    print("[ingest] Starting ingestion pipeline...")

    dim = await probe_embedding_dim()
    await ensure_collection(dim)

    raw = json.loads(DATASET_PATH.read_text(encoding="utf-8"))
    passages = raw if isinstance(raw, list) else raw.get("data", [])
    print(f"[ingest] Loaded {len(passages)} records from dataset.")

    completed_hashes = load_checkpoint()
    print(f"[ingest] Resuming — {len(completed_hashes)} hashes already confirmed.")

    # Build the work queue: deduplicate by text hash, skip checkpointed hashes
    queue: list[dict[str, Any]] = []
    seen: set[str] = set()
    for record in passages:
        text: str = record.get("context", "").strip()
        if not text:
            continue
        h = hashlib.sha256(text.encode()).hexdigest()
        if h in seen or h in completed_hashes:
            continue
        seen.add(h)
        tok = token_count(text)
        if tok > MAX_TOKENS_WARN:
            print(f"[warn] id={record.get('id', '?')} has {tok} tokens — may be truncated by API")
        queue.append({
            "id": str(record.get("id", h)),
            "text": text,
            "hash": h,
            "payload": {
                "title": record.get("title", ""),
                "source_doc": record.get("title", ""),
                "passage_id": str(record.get("id", "")),
                "text": text,
            },
        })

    print(f"[ingest] {len(queue)} passages to embed and upsert.")

    for batch_start in range(0, len(queue), BATCH_SIZE):
        batch = queue[batch_start: batch_start + BATCH_SIZE]
        embeddings = await embed_batch([p["text"] for p in batch])

        points = [
            PointStruct(id=p["id"], vector=vec, payload=p["payload"])
            for p, vec in zip(batch, embeddings)
        ]

        result = await qdrant.upsert(
            collection_name=COLLECTION_NAME,
            points=points,
            wait=True,   # block until Qdrant confirms write before checkpointing
        )

        if result.status != UpdateStatus.COMPLETED:
            raise RuntimeError(f"Qdrant upsert returned status: {result.status}")

        for p in batch:
            completed_hashes.add(p["hash"])
        save_checkpoint(completed_hashes)

        print(f"[ingest] Batch {batch_start // BATCH_SIZE + 1}: "
              f"{batch_start + len(batch)}/{len(queue)} upserted.")
        await asyncio.sleep(3)   # polite delay — respects free-tier 20 req/min

    print("[ingest] All passages upserted. Running sanity check...")
    await sanity_check()


# ── Post-ingestion sanity check ────────────────────────────────────────────────
async def sanity_check() -> None:
    """
    Embed the first corpus passage and assert it ranks #1 in Qdrant.
    Validates distance metric, embedding pipeline, and collection integrity.
    Fails loudly — never silently pass with a low score.
    """
    raw = json.loads(DATASET_PATH.read_text(encoding="utf-8"))
    passages = raw if isinstance(raw, list) else raw.get("data", [])
    first_text = passages[0]["context"].strip()

    vecs = await embed_batch([first_text])
    results = await qdrant.search(
        collection_name=COLLECTION_NAME,
        query_vector=vecs[0],
        limit=1,
        with_payload=True,
    )

    top = results[0]
    assert top.score > 0.99, (
        f"Sanity check FAILED: top score={top.score:.4f} (expected >0.99). "
        f"Check distance metric and embedding dimension."
    )
    print(f"[sanity] PASS — score={top.score:.4f}, id={top.id}")


if __name__ == "__main__":
    asyncio.run(ingest())
```

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `AsyncOpenAI(base_url=...)` | OpenAI SDK client re-pointed at OpenRouter's OpenAI-compatible endpoint — covers both embeddings and chat completions, no separate SDK needed | Initialise once at module level with `base_url="https://openrouter.ai/api/v1"`; reuse across all embed and chat calls |
| `AsyncQdrantClient` | Official async Python client for Qdrant — uses `httpx.AsyncClient` internally; never use the sync `QdrantClient` in FastAPI or any async context | Initialise once with `host`, `port`, `api_key`; passed into all retrieval and upsert functions |
| `PointStruct(id, vector, payload)` | The unit of data in Qdrant — one passage = one point. `id` must be a UUID string or integer. `payload` is arbitrary JSON (title, source_doc, text) returned with search results for citation rendering | Used in every `upsert()` call; `payload` drives Phase 2 citation construction |
| `VectorParams(size, distance)` | Collection-level schema for the vector space — `size` must match the probed embedding dimension exactly; `distance` is **immutable after collection creation** | Set once during `create_collection()`; probe dimension from first API call before calling this |
| `pydantic-settings BaseSettings` | Reads environment variables and `.env` files with type validation — raises `ValidationError` at import time if required fields are missing, preventing silent misconfiguration | Used in `config.py`; every module imports `get_settings()` wrapped in `@lru_cache` for a singleton |

### Common Pitfalls

1. **Using the sync `QdrantClient` in an async context** — The synchronous client uses `requests` under the hood and calls `threading.Event.wait()` inside an async function, which blocks the entire asyncio event loop for the duration of every Qdrant call. In FastAPI with concurrent requests this serialises all database operations. Always import `AsyncQdrantClient` from `qdrant_client`. The sync client is only safe in standalone non-async scripts with no FastAPI involvement.

2. **Qdrant bind mount on Windows/WSL2 destroys data** — Using `./qdrant_data:/qdrant/storage` in `docker-compose.yml` routes Qdrant's Write-Ahead Log through the Windows NTFS/hypervisor filesystem layer. The WAL silently corrupts or loses data across container restarts. From Qdrant v1.15.0 onwards, Qdrant performs a POSIX filesystem compatibility check at startup and **refuses to start** if the check fails. Always use a named Docker volume (`qdrant_storage:/qdrant/storage`) — never a Windows `D:\...` bind mount path. This is a day-1 decision that is painful to fix retroactively.

3. **Hardcoding Nemotron embedding dimension** — Nemotron's output vector size is not published in OpenRouter's API docs or NVIDIA's model card. If you hardcode a guess (768, 1024, 1536) and it is wrong, `create_collection()` succeeds, but subsequent `upsert()` calls fail with a dimension mismatch error — or worse, silently accept a different model's embeddings on a later re-run after a client swap. Always probe: call `embeddings.create(input="probe")` and read `len(resp.data[0].embedding)`. Cache this value for the lifetime of the ingestion script.

4. **Not using `wait=True` in `upsert()` during ingestion** — Without `wait=True`, Qdrant accepts the upsert request asynchronously and returns immediately. The ingestion checkpoint records the batch as complete, but if the process crashes or Docker is stopped before Qdrant flushes to disk, the data is silently lost while the checkpoint says it was saved. On re-run, those hashes are in the checkpoint and are skipped — the gap is permanent. Use `wait=True` for the one-shot ingestion script; reserve `wait=False` only for high-throughput streaming writes that accept eventual consistency.

5. **Silent embedding truncation on long passages (Pitfall C6)** — OpenRouter returns HTTP 200 and a valid embedding for inputs that exceed the model's maximum token length. The embedding silently represents only the first N tokens of the passage. No error is raised, no warning is logged. For passages beyond ~512 tokens, the tail of the passage (often the most specific clause language) is dropped from the embedding, causing retrieval failures on queries about that content. Always count tokens with `tiktoken` before calling the embedding API. Warn and flag any passage exceeding 400 tokens for review during ingestion.

## 4. Implementation Guidance

**Model Configuration:**

| Parameter | Value | Notes |
|-----------|-------|-------|
| Embedding model | `nvidia/llama-nemotron-embed-vl-1b-v2` | Via OpenRouter; use `:free` suffix for free tier during development |
| LLM model (Phase 2+) | `google/gemma-4-26b-a4b` | Not used in Phase 1 ingestion pipeline |
| Embedding batch size | 50 texts per API request | Conservative for OpenRouter free tier (20 req/min); increase to 100 on paid tier |
| Chunk token target | 400 tokens | Measured with `tiktoken cl100k_base`; leaves a safety margin under Nemotron's practical ~512 token limit |
| Chunk overlap | 50 tokens | ~12.5% overlap; preserves clause continuity across chunk boundaries |
| Qdrant distance | `Distance.COSINE` | Nemotron outputs L2-normalised vectors; COSINE and DOT-product are mathematically equivalent, COSINE is conventional |
| `upsert(wait=True)` | Always in ingestion script | Ensures checkpoint only records confirmed disk writes |
| Inter-batch sleep | 3 seconds | Respects OpenRouter free-tier 20 req/min limit; reduce to 0.5s on paid tier |

**Core Pattern:**

The ingestion pipeline is a linear five-step sequence with no branching or framework:

```
1. probe_embedding_dim()     — one API call; determines Qdrant collection size
2. ensure_collection(dim)    — create 'policies' collection if not exists; COSINE distance
3. load + validate corpus    — pydantic PolicyPassage model; skip empty/invalid records
4. dedup by SHA-256 hash     — skip passages already in checkpoint or seen in this run
5. for each batch of 50:
       embed_batch(texts)    — AsyncOpenAI; exponential backoff on 429
       qdrant.upsert(points, wait=True)
       save_checkpoint()
6. sanity_check()            — embed first passage; assert it ranks #1 in Qdrant
```

This maps directly to six `await` calls in a single `async def ingest()` function. There is no framework mediating these steps.

**Tool Use:**

| Tool / Integration | Purpose | How to Configure |
|--------------------|---------|-----------------|
| `AsyncOpenAI` | Embedding API calls to OpenRouter | `base_url="https://openrouter.ai/api/v1"`, `api_key=settings.openrouter_api_key`, `default_headers` with optional attribution |
| `AsyncQdrantClient` | Vector store upsert + search | `host=settings.qdrant_host`, `port=settings.qdrant_port`, `api_key=settings.qdrant_api_key` |
| `tiktoken` | Token counting before embed (C6 guard) | `tiktoken.get_encoding("cl100k_base")`; call `len(enc.encode(text))` before each embed call |
| `pydantic-settings` | `.env` loading with validation | `class Settings(BaseSettings)` with `model_config = {"env_file": ".env"}`; missing required fields raise `ValidationError` at startup |
| `hashlib.sha256` | Per-passage deduplication key | Hash `context` text bytes; skip if hash in checkpoint or Qdrant payload filter |

**State Management:**

Phase 1 has two durable state surfaces:

1. **Checkpoint file** (`ingestion_checkpoint.json`, gitignored) — a JSON file written to disk after each confirmed batch. Structure: `{"completed_hashes": ["sha256hex", ...]}`. On re-run, batches whose text hashes are already in the checkpoint are skipped entirely without making any API calls. Safe to delete to trigger a full re-ingest from scratch.

2. **Qdrant `policies` collection** — the primary durable output of Phase 1. Persisted on the named Docker volume `qdrant_storage`. `upsert()` is idempotent by point `id` — upserting the same id a second time overwrites the payload and vector. This makes partial re-ingest safe without duplicates. The `wait=True` flag ensures the checkpoint only advances after Qdrant confirms the write.

There is no in-memory state beyond the current batch — every batch is flushed to Qdrant and the checkpoint before the next begins.

**Context Window Strategy:**

Phase 1 is ingestion-only; there is no LLM involved. However, chunking decisions made here directly constrain Phase 2 retrieval quality and cannot be changed without re-ingesting:

- Target 400 tokens per chunk with 50-token overlap. This keeps chunks under Nemotron's safe embedding limit while providing enough clause context for the Phase 2 LLM to form an answer.
- Use semantic separator priority: `["\n\n", "\n", ". ", " "]`. Split at paragraph boundaries first, then sentence, never mid-word.
- Treat numbered list items and table rows as atomic units. A "data retention: 30 days" row in a policy table must not be split from its column header.
- Every chunk's Qdrant payload must carry `title`, `source_doc`, `passage_id`, and `text`. Phase 2 cannot construct inline citations without `source_doc` — passages without it cannot be cited and are dead weight in the index.
- At retrieval time (Phase 2), top-5 x 400 tokens = 2,000 tokens of retrieved context. Add system prompt (~200 tokens) + user query (~50 tokens): total ~2,250 tokens — well under Gemma 4 26B's 131,072 token context window. No truncation strategy is needed at Phase 2's scale.

### 4b.1 Structured Outputs with Pydantic

For Phase 1, Pydantic serves two purposes: startup config validation via `pydantic-settings`, and corpus record validation before embedding.

The service never starts in a silent broken state. The `@lru_cache` decorator ensures `Settings()` is instantiated only once per process — safe and efficient.

**Corpus record validation — ingestion guard:**

```python
# backend/ingestion/ingest.py
from pydantic import BaseModel, field_validator

class PolicyPassage(BaseModel):
    id: str | int
    title: str
    context: str

    @field_validator("context")
    @classmethod
    def context_not_empty(cls, v: str) -> str:
        v = v.strip()
        if not v:
            raise ValueError("context is empty")
        return v

# Validate every record before it enters the embedding queue
valid: list[PolicyPassage] = []
skipped = 0
for raw_record in raw_data:
    try:
        valid.append(PolicyPassage(**raw_record))
    except Exception as exc:
        skipped += 1
        print(f"[skip] Invalid record id={raw_record.get('id', '?')}: {exc}")

print(f"[parse] {len(valid)} valid passages, {skipped} skipped.")
```

### 4b.2 Async-First Design

**How async works in this stack:**

Both `AsyncOpenAI` and `AsyncQdrantClient` use `httpx.AsyncClient` internally. Every network-bound method returns a coroutine and must be `await`ed. The ingestion script uses `asyncio.run(ingest())` as its entry point. FastAPI's lifespan hook (`async def lifespan(app)`) is also async — collection bootstrap calls must be `await`ed there, never wrapped in `asyncio.run()`.

**The one critical mistake — `asyncio.run()` inside an already-running event loop:**

```python
# WRONG — raises RuntimeError: "This event loop is already running"
# Occurs when called from a FastAPI startup handler, Jupyter notebook,
# or any context where asyncio already has a running loop.
@asynccontextmanager
async def lifespan(app: FastAPI):
    asyncio.run(ensure_collection(dim))   # DO NOT do this
    yield

# CORRECT — await the coroutine directly inside the already-running loop
@asynccontextmanager
async def lifespan(app: FastAPI):
    dim = await probe_embedding_dim()
    await ensure_collection(dim)
    yield
```

The ingestion script is a standalone process (`python -m backend.ingestion.ingest`) and is never imported from FastAPI. Only the lightweight `ensure_collection()` check runs in FastAPI's lifespan — not the full ingestion loop.

**Concurrency within ingestion — when to use `asyncio.gather()`:**

The current design embeds and upserts batches sequentially with a 3-second sleep. This is intentional for the free tier (20 req/min). On a paid OpenRouter account, replace the sequential loop with concurrent batch processing:

```python
# Paid-tier concurrent ingestion (verify rate limit headroom first)
tasks = [
    embed_and_upsert(batch)
    for batch in chunks(queue, BATCH_SIZE)
]
await asyncio.gather(*tasks)
```

Do not use `asyncio.gather()` on the free tier — it fans out all requests simultaneously and triggers 429 errors on the first batch.

**Stream vs. await decision table:**

| Pattern | Use Case | Phase 1 Relevance |
|---------|----------|-------------------|
| `await embeddings.create(...)` | Structured vector output — must be complete before upserting | Always await for embeddings |
| `await qdrant.upsert(..., wait=True)` | Write confirmation before checkpointing | Always await with `wait=True` in ingestion |
| `async for chunk in stream` | LLM token streaming to frontend — reduces perceived latency | Not in Phase 1; applies to Phase 2 chat endpoint with `StreamingResponse` |

### 4b.3 Prompt Engineering Discipline

Phase 1 contains no LLM prompts. This section records the constraints that Phase 1 ingestion decisions impose on Phase 2 prompt design — document now so Phase 2 does not have to reverse-engineer ingestion choices.

**System vs. user prompt separation — pattern established by Phase 1 payload fields:**

```python
# Phase 2 prompt pattern — the payload fields defined in Phase 1 ingestion drive this
SYSTEM_PROMPT = """You are a privacy policy compliance assistant.
Answer questions using ONLY the policy passages provided below.
Each passage is labeled with a numeric ID: [1], [2], etc.
You MUST cite sources using only these numeric IDs.
Do not cite any source, document name, or section not present in the numbered passages.
If the provided passages do not contain sufficient information to answer, respond exactly:
"I could not find this in the provided policies." """

def build_user_message(query: str, retrieved_points: list) -> str:
    # retrieved_points come from qdrant.search() — payload.text and payload.source_doc
    # are set during Phase 1 ingestion; missing these fields breaks citation rendering
    context_block = "\n\n".join(
        f"[{i + 1}] Source: {p.payload['source_doc']}\n{p.payload['text']}"
        for i, p in enumerate(retrieved_points)
    )
    return f"Policy Passages:\n{context_block}\n\nQuestion: {query}"
```

**Token budget — always set `max_tokens` explicitly:**

Never leave `max_tokens` unset in production. Gemma 4 26B via OpenRouter charges per output token. An unbounded response on a system with 1,000 queries/day at $0.0003/token creates unpredictable cost. Set:
- Standard answer: `max_tokens=800`
- Conflict analysis (multi-document): `max_tokens=1500`
- Classification / routing sub-task: `max_tokens=50`

**Few-shot examples:** Inline 2–3 examples in the system prompt (not dynamic retrieval) to teach citation format. Each example should be under 100 tokens. Dynamic few-shot retrieval adds latency and complexity with no demonstrated benefit for a fixed citation format task.

### 4b.4 Context Window Management

**Phase 1 chunking decisions are permanent — they define the retrieval unit for all subsequent phases:**

| Decision | Value | Why This Value |
|----------|-------|----------------|
| Chunk size | 400 tokens | Below Nemotron's safe embedding limit (~512 tokens); provides enough legal clause context for the LLM |
| Overlap | 50 tokens | Preserves sentence continuity at boundaries without inflating index size significantly |
| Separator order | `["\n\n", "\n", ". ", " "]` | Paragraphs first; never split mid-sentence in legal text |
| Atomic units | Numbered list items, table rows | Legal obligations embedded in lists must include their context row |
| Required payload fields | `title`, `source_doc`, `passage_id`, `text` | Phase 2 cannot cite passages without `source_doc`; `text` enables verbatim quote display |

**Phase 2 context budget (pre-computed from Phase 1 choices):**

```
top-5 chunks x 400 tokens = 2,000 tokens of retrieved context
system prompt             =   ~200 tokens
user query                =    ~50 tokens
─────────────────────────────────────────
total prompt              = ~2,250 tokens   (1.7% of Gemma 4 26B's 131,072 limit)
```

At this scale, no truncation or summarisation strategy is needed. The `score_threshold` parameter in `qdrant.search()` (set to 0.55 as a starting point) prevents padding the prompt with low-relevance passages.

**When context budget pressure appears (flag for Phase 3):**

- Cross-document conflict analysis retrieves top-10 across two documents: ~4,500 tokens total — still safe.
- If retrieval expands to top-20 for multi-hop queries: ~8,200 tokens — still under limit, but consider implementing a reranker to select the 5 most relevant from a top-20 candidate set before injecting into the prompt.

### 4b.5 Cost and Latency Budget

**Phase 1 — one-time ingestion cost:**

| Item | Value |
|------|-------|
| Total passages | ~17,000 |
| Batches at 50/batch | 340 API requests |
| Free-tier limit | 200 req/day — requires 2 calendar days minimum at free tier |
| Paid-tier embedding cost | ~400 tokens/chunk x 17K passages = 6.8M tokens; Nemotron via OpenRouter ≈ $0.00007/1K tokens = **~$0.48 total** |
| Estimated runtime (free tier) | 340 batches x 3s sleep = ~17 minutes of active execution + 2-day spread |
| Estimated runtime (paid tier) | ~6–8 minutes end-to-end without rate-limit sleeps |
| Qdrant storage | ~17K x vector size bytes per point; negligible at this scale |

**Phase 2 per-query cost (reference for planning):**

| Step | Model | Latency | Cost per Query |
|------|-------|---------|----------------|
| Embed query | Nemotron (OpenRouter) | ~200ms | ~$0.000028 |
| Qdrant vector search | Local Docker | ~50ms | $0.00 |
| LLM generation | Gemma 4 26B (OpenRouter) | ~2–8s streaming first token ~500ms | ~$0.0003–0.0012 |
| **Total** | | **~2.3–8.3s** | **~$0.0003–0.0015** |

At 1,000 queries/day: ~$0.30–1.50/day. At 5,000 queries/day: ~$1.50–7.50/day.

**Caching strategy (implement in Phase 2):**

1. **Query embedding cache** — identical query strings produce identical embeddings (embeddings are deterministic). Cache with `functools.lru_cache` keyed by query string for single-process dev; Redis for multi-worker production. Eliminates 200ms + $0.000028 per repeated FAQ query.

2. **Response cache** — for the top 20 most common compliance questions, cache the full LLM response keyed by `(query_hash, frozenset(top_k_point_ids))`. Invalidate on corpus re-ingestion. Reduces $0.001/query to $0.00 for cached responses.

3. **Cheaper model for sub-tasks** — if query routing or intent classification is added (Phase 3), use a smaller model at 1/10th the cost. The main generation model (Gemma 4 26B) is reserved for answer synthesis only.

## 5. Evaluation Strategy

> Phase 1 is an infrastructure and data ingestion phase — there is no LLM inference involved. All evaluation dimensions are code-based correctness checks, not LLM judges. The eval suite is a set of executable pytest scripts that can be run after every ingestion run and in CI/CD. INGEST-06 (sanity check) is mandatory before any Phase 2 work begins.

### Dimensions

| # | Dimension | PASS | FAIL | Measurement | Priority |
|---|-----------|------|------|-------------|----------|
| 1 | **Embedding dimension probe correctness** | `probe_embedding_dim()` returns a positive integer that matches `len(resp.data[0].embedding)` from a live Nemotron API call; the value is used (not a hardcoded constant) to create the Qdrant collection | `create_collection()` is called with a hardcoded size (768, 1024, 1536, etc.) rather than the probed value; or probe returns 0 | Code — assert `dim > 0` and `collection.config.params.vectors.size == dim` via `qdrant.get_collection()` | Critical |
| 2 | **Distance metric correctness** | Qdrant `policies` collection reports `distance: Cosine` when inspected via `qdrant.get_collection("policies").config.params.vectors.distance` | Collection reports `Dot` or `Euclid`; or collection does not exist | Code — `assert collection_info.config.params.vectors.distance == Distance.COSINE` | Critical |
| 3 | **Rank-1 sanity check (INGEST-06)** | A known passage embedded and queried against Qdrant returns itself as the top-1 result with cosine score > 0.99 | Top-1 result is a different passage; or top-1 score is <= 0.99; or search returns zero results | Code — `sanity_check()` function in `ingest.py`; assert `results[0].score > 0.99` | Critical |
| 4 | **Index completeness — point count** | `qdrant.get_collection("policies").points_count` equals the number of unique deduplicated passages loaded from the dataset JSON (within a 0.1% tolerance to allow for legitimate skips of empty/invalid records) | Point count is more than 1% below the expected unique passage count — indicating silent batch drops during ingestion | Code — compare `points_count` against `len(deduplicated_corpus)` after ingestion; assert `abs(actual - expected) / expected < 0.001` | High |
| 5 | **Metadata completeness (INGEST-03)** | Every Qdrant point retrieved via scroll has all four required payload fields present and non-empty: `title`, `source_doc`, `passage_id`, `text` | Any point has a missing, null, or empty-string value for `title`, `source_doc`, `passage_id`, or `text`; or payload is an empty dict | Code — scroll a random sample of 200 points post-ingestion; assert all four fields are non-empty strings on every sampled point | High |
| 6 | **Deduplication integrity** | After ingestion, querying Qdrant for a known-duplicate passage (same text, different `id`) returns exactly one point; checkpoint hashes contain no duplicates | Two or more Qdrant points have identical `text` payload values; or checkpoint file contains the same hash twice | Code — SHA-256 hash all `text` payloads from a scroll of all points; assert `len(hashes) == len(set(hashes))` | High |
| 7 | **Checkpoint resumability** | Simulated mid-run failure: truncate checkpoint to 50% of completed hashes, re-run ingest, verify only missing passages are re-embedded; final point count is unchanged | Re-run re-embeds already-checkpointed passages (wasted API calls) or creates duplicate points; or re-run fails with an exception on a clean dataset | Code — integration test: run ingest to 50% completion, kill process, verify checkpoint, re-run, assert final `points_count` equals single full-run result | High |
| 8 | **Rate-limit backoff correctness** | When OpenRouter returns HTTP 429, `embed_batch()` retries with exponential backoff (1s, 2s, 4s, 8s, 16s delays); after 5 retries it raises `RuntimeError`, not silently returns empty results | `embed_batch()` raises immediately on 429 without retry; or retries indefinitely without raising; or returns `[]` on failure | Code — mock the OpenRouter client to raise a 429 exception; assert retry count and final exception type with `pytest` + `unittest.mock` | Medium |
| 9 | **Token count guard (C6)** | All passages with token count > 400 (measured by `tiktoken cl100k_base`) are logged as warnings before embedding; no passage exceeds 512 tokens without a log entry | Passages above 400 tokens are silently embedded without a warning; or passages above 512 tokens enter the embed queue without truncation detection | Code — after ingestion, scan logs for token warning entries; separately assert that any passage > 512 tokens in the dataset was flagged | Medium |
| 10 | **Qdrant volume persistence** | After `docker compose down && docker compose up`, `qdrant.get_collection("policies").points_count` equals the pre-restart count | Point count drops to 0 or errors after container restart — indicates bind mount data loss (Pitfall C2) | Code — integration test: record count, `docker compose restart qdrant`, assert count unchanged; run only in environments with Docker | Medium |

```python
async def test_index_completeness(qdrant):
    """Point count must be within 0.1% of deduplicated corpus size."""
    raw = json.loads(DATASET_PATH.read_text(encoding="utf-8"))
    passages = raw if isinstance(raw, list) else raw.get("data", [])
    unique_texts = {p["context"].strip() for p in passages if p.get("context", "").strip()}
    expected = len(unique_texts)

@pytest.mark.asyncio
async def test_metadata_completeness(qdrant):
    """Random sample of 200 points must all have title, source_doc, passage_id, text."""
    required_fields = {"title", "source_doc", "passage_id", "text"}
    points, _ = await qdrant.scroll(
        collection_name=COLLECTION_NAME,
        limit=SAMPLE_SIZE,
        with_payload=True,
    )
    for point in points:
        missing = required_fields - set(point.payload.keys())
        assert not missing, f"Point id={point.id} missing payload fields: {missing}"
        for field in required_fields:
            assert point.payload[field], f"Point id={point.id} has empty value for field '{field}'"

@pytest.mark.asyncio
async def test_no_duplicate_passages(qdrant):
    """All text payloads in the index must be unique."""
    all_texts = []
    offset = None
    while True:
        points, next_offset = await qdrant.scroll(
            collection_name=COLLECTION_NAME, limit=500, offset=offset, with_payload=True
        )
        all_texts.extend(p.payload.get("text", "") for p in points)
        if next_offset is None:
            break
        offset = next_offset
    hashes = [hashlib.sha256(t.encode()).hexdigest() for t in all_texts]
    assert len(hashes) == len(set(hashes)), (
        f"Found {len(hashes) - len(set(hashes))} duplicate passages in Qdrant. "
        "Deduplication logic in ingest.py may have failed."
    )
```

## 6. Guardrails

> Phase 1 has no user-facing requests — it is a one-shot offline ingestion process. Traditional "online" guardrails (per-request safety filters) do not apply. The guardrails here are ingestion-time hard stops and post-ingestion integrity gates that prevent a broken index from being handed to Phase 2.

### Online (Real-Time — Ingestion Process Guards)

These run synchronously inside the ingestion script itself. Each is a hard stop: the script raises an exception and exits rather than continuing with corrupt state.

| Guardrail | Trigger Condition | Intervention |
|-----------|------------------|--------------|
| **Dimension mismatch hard stop** | `probe_embedding_dim()` returns a value that does not match an existing collection's vector size (detected if collection already exists from a prior run with a different model) | Block — raise `RuntimeError("Dimension mismatch: existing collection uses dim={existing}, Nemotron returned dim={probed}. Delete collection and re-run.")` before any upsert |
| **Distance metric guard** | After `ensure_collection()`, `get_collection().config.params.vectors.distance != Distance.COSINE` | Block — raise `RuntimeError("Collection distance metric is not COSINE. Delete collection and re-ingest.")` — wrong metric is unrecoverable without full re-ingest |
| **Upsert failure hard stop** | `qdrant.upsert()` returns `UpdateStatus` other than `COMPLETED` | Block — raise `RuntimeError(f"Qdrant upsert returned status: {result.status}")` before advancing checkpoint — prevents checkpoint from recording a failed write as succeeded |
| **Empty corpus guard** | Dataset JSON loads 0 valid `PolicyPassage` records after Pydantic validation | Block — raise `ValueError("No valid passages found in dataset. Check DATASET_PATH and corpus format.")` before making any API calls |
| **API key validation** | `pydantic-settings` `Settings()` instantiation fails with `ValidationError` (missing `OPENROUTER_API_KEY`) | Block — `ValidationError` propagates to caller with field-level message; ingestion never starts |

### Offline (Flywheel — Post-Ingestion Quality Gates)

These run after ingestion completes, via `make eval-ingest`. They feed the improvement loop: if any check fails, the ingestion output is not trusted for Phase 2 work.

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|-----------------------|
| **Rank-1 sanity score** (INGEST-06) | Fixed probe: first corpus passage, run after every ingestion | If score <= 0.99: investigate distance metric and embedding pipeline before proceeding to Phase 2. Likely cause: collection recreated with wrong metric, or Nemotron model changed |
| **Index completeness ratio** (`points_count / expected_unique`) | Full collection count check, O(1) via `get_collection()` | If ratio < 0.999: identify missing batch range from checkpoint file; delete collection and re-run ingestion from scratch |
| **Metadata completeness rate** (sampled) | Random 200-point scroll after each ingestion run | If any sampled point is missing `source_doc` or `text`: fix chunker metadata propagation bug; re-ingest affected `source_doc` using Qdrant payload filter delete + partial re-run |
| **Duplicate passage rate** | Full scroll hash check, run once post-ingestion | If any duplicates found: review dedup logic in `ingest.py`; use Qdrant `delete` by duplicate IDs; re-run dedup verification |
| **Token over-limit passage count** | Scan ingestion logs for `[warn]` lines after each run | If > 5% of passages flagged at > 400 tokens: review chunker splitting logic; passages above 512 tokens require re-chunking before re-embedding |

## 7. Production Monitoring

> Phase 1 is a one-shot ingestion script, not a persistent service — "production monitoring" here means post-ingestion health visibility and the observability infrastructure that will serve Phase 2+. Arize Phoenix is introduced now so tracing is operational when the RAG pipeline goes live in Phase 2.

### Tracing Tool

**Selected: Arize Phoenix (self-hosted, open-source)**

No LangChain or LlamaIndex is used in this project (prohibited by CLAUDE.md), so LangSmith is not applicable. Phoenix is framework-agnostic via OpenTelemetry and integrates with the raw `openai` SDK through its `OpenAIInstrumentor`. It runs as a Docker Compose service alongside Qdrant — zero external accounts or cloud cost.

**Add to `docker-compose.yml`:**

```yaml
services:
  phoenix:
    image: arizephoenix/phoenix:latest
    ports:
      - "6006:6006"   # UI
      - "4317:4317"   # OTLP gRPC ingest
    restart: unless-stopped
```

**Install:**

```bash
pip install arize-phoenix opentelemetry-sdk opentelemetry-exporter-otlp openinference-instrumentation-openai
```

**Instrument (add to `backend/app/core/telemetry.py`, import in `main.py` lifespan):**

```python
# backend/app/core/telemetry.py
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from openinference.instrumentation.openai import OpenAIInstrumentor

def setup_tracing(endpoint: str = "http://phoenix:4317") -> None:
    """
    Call once at FastAPI startup (lifespan). Instruments the openai client
    so every embeddings.create() and chat.completions.create() call is traced
    automatically — no manual span creation needed in application code.
    """
    exporter = OTLPSpanExporter(endpoint=endpoint)
    provider = TracerProvider()
    provider.add_span_processor(BatchSpanProcessor(exporter))
    trace.set_tracer_provider(provider)
    OpenAIInstrumentor().instrument()
```

Phoenix UI is available at `http://localhost:6006` after `docker compose up phoenix`.

**Phase 1 note:** The ingestion script runs outside FastAPI's lifecycle. To trace ingestion runs, call `setup_tracing()` at the top of `ingest.py` before the first `embed_batch()` call. This records every OpenRouter embedding call with token counts, latency, and response metadata — useful for diagnosing rate-limit patterns and per-batch timing.

### Key Metrics to Track

These are the five metrics that matter across Phase 1 (ingestion health) and Phase 2+ (RAG quality). The first three are available immediately after ingestion; the last two activate in Phase 2.

| Metric | What It Measures | Where to Read It |
|--------|-----------------|-----------------|
| **`points_count`** | Total passages indexed in Qdrant — primary completeness signal | `qdrant.get_collection("policies").points_count` via REST or Phoenix span metadata |
| **Rank-1 sanity score** | Cosine similarity of first corpus passage to itself — proxy for distance metric and embedding pipeline health | `pytest eval-ingest` output; log to stdout after each ingestion run |
| **OpenRouter 429 rate** | Frequency of rate-limit retries during ingestion — indicates whether batch sizing and sleep delays are calibrated correctly | Ingestion stdout `[rate_limit]` log lines; Phoenix spans show retry attempts as child spans |
| **Embedding call latency p95** | 95th percentile latency per `embeddings.create()` batch call — baseline for Phase 2 query latency budget | Phoenix trace timeline; visible per-span in Phoenix UI after Phase 2 instrumentation |
| **Passages with token count > 400** | Count of corpus passages that may be silently truncated by Nemotron — indicates chunker tuning needed | Ingestion stdout `[warn]` log lines; count and review before Phase 2 |

### Alert Thresholds

Phase 1 has no always-on service to alert. Instead, these are **ingestion run exit criteria** — conditions that must be resolved before Phase 2 work begins:

| Condition | Threshold | Required Action |
|-----------|-----------|----------------|
| Rank-1 sanity score | Must be > 0.99 | Do not proceed to Phase 2. Debug distance metric and re-ingest. |
| Index completeness ratio | Must be >= 99.9% of expected unique passage count | Identify missing batches from checkpoint; delete collection and re-ingest. |
| Any metadata field missing | Zero tolerance — 0 points with missing `title`, `source_doc`, `passage_id`, or `text` | Fix chunker metadata propagation; re-ingest affected source documents. |
| Duplicate passages | Zero tolerance — 0 duplicate `text` hashes in index | Identify and delete duplicate points; fix dedup logic before next run. |
| OpenRouter 429 retries | > 20% of batches triggered at least one retry | Increase `BATCH_SLEEP` from 3s to 5s; or switch to paid tier before continuing. |

**For Phase 2+ (persistent FastAPI service):** Set the following Phoenix-based alerts once the chat endpoint is live:

| Metric | Alert Threshold | Severity |
|--------|----------------|----------|
| Query embedding latency p95 | > 1,000ms | Warning — investigate OpenRouter free-tier congestion |
| Qdrant search latency p95 | > 500ms | Warning — check Docker resource allocation |
| OpenRouter 5xx error rate | > 1% of requests in any 5-minute window | Critical — circuit breaker; return "service temporarily unavailable" |

### Smart Sampling Strategy

**Phase 1 — ingestion run sampling:**

Every ingestion run logs a structured summary to stdout. The QA Engineer reviews this after each run (not sampled — it is a complete run summary):

```
[ingest_summary] passages_loaded=17284 deduped=16991 skipped_empty=12 
                 skipped_checkpoint=0 upserted=16991 token_warnings=47 
                 rate_limit_retries=3 duration_seconds=1042
```

Flag any run where `token_warnings / upserted > 0.05` (more than 5% of passages over the token limit) — this indicates the chunker is not splitting long passages correctly.

**Phase 2+ — production query sampling:**

Once the chat endpoint is live, select interactions for human review using signal-based filters (not random sampling):

| Filter | Rationale | Review Frequency |
|--------|-----------|-----------------|
| Qdrant top-1 score between 0.55 and 0.65 | Low-confidence retrievals — system is close to the abstain threshold; may be returning marginally relevant passages | Weekly batch: review 20 sampled queries from this score band |
| Query contains "Decree 13", "PDPL", "Nghị định 13" | High-stakes jurisdiction-specific queries — most likely to produce jurisdiction misattribution errors | Weekly batch: review 100% of these queries for the first month |
| System returned "no matching policy found" | Abstain responses — verify the corpus genuinely lacks the answer; if not, indicates retrieval gap | Weekly batch: review 100% of abstain responses |
| User reformulated the same question within the same session | Implicit dissatisfaction signal — user was not satisfied with the first answer | Review all occurrences; flag for Phase 2 retrieval improvement |

Human reviewer: Compliance Analyst or DPO (see Domain Expert Roles in Section 1b). Review sessions: 30 minutes weekly during the first month post-launch; reduce to bi-weekly once error rate stabilizes below 2%.
